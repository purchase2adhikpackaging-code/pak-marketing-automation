# PAK Marketing Automation — Integration Specification

**Document ID:** PAK-INT-001  
**Version:** 1.2  
**Status:** Current baseline through Organization Profile / Brand Kit / Knowledge ingestion foundation

## 1. Integration principles

- **INT-GEN-001** Provider-specific SDKs/payloads stay behind adapter interfaces.
- **INT-GEN-002** Organization provider secrets are server/Edge-resolved and organization-scoped.
- **INT-GEN-003** Browser clients never receive stored raw secrets.
- **INT-GEN-004** Integrations expose normalized health/status metadata.
- **INT-GEN-005** External side effects use idempotency/reconciliation wherever provider semantics allow.
- **INT-GEN-006** Provider errors are normalized and secrets redacted before persistence/UI.
- **INT-GEN-007** CI uses deterministic fakes; live provider calls are controlled verification only.
- **INT-GEN-008** Paid provider execution may not trust browser-submitted provider prompt/model/configuration when authoritative approved domain state exists.
- **INT-GEN-009** Ephemeral provider result or Storage signed URLs are transport-only and are not durable PAK media/Brand identity.
- **INT-GEN-010** Organization Profile, Brand Kit and Knowledge are internal authoritative data sources, not browser-supplied integration payloads.
- **INT-GEN-011** Uploaded binaries reuse the private Media Library rather than creating integration-specific storage silos.

## 2. Integration Vault contract

Current provider connection model:
`integration_connections` → `integration_secrets.vault_secret_id` → Supabase Vault
with immutable `integration_audit_events`.

Provider states:
`NOT_CONFIGURED | CONFIGURED | INVALID | DISABLED`.

Server/Edge responsibilities:
- resolve safe non-secret connection metadata;
- resolve raw secret only inside privileged runtime;
- save/replace/remove through narrowly scoped privileged RPCs;
- never return raw secret after save;
- record immutable audit metadata;
- normalize provider validation results.

## 3. OpenAI — IMPLEMENTED

### Purpose
Canonical scripts, translations, Scene Planning assistance and approved structured AI assistance.

### Secret
- `API_KEY`

### Rules
- **INT-OAI-001** Key is stored through Integration Vault and never returned after save.
- **INT-OAI-002** Provider adapter resolves organization-scoped credential at runtime.
- **INT-OAI-003** Model is configuration, not secret.
- **INT-OAI-004** Grounded generation receives server-composed bounded context only.
- **INT-OAI-005** Current canonical generation context is Profile → Brand Kit → ACTIVE Core Knowledge → selected ACTIVE Knowledge → task context.
- **INT-OAI-006** Browser-selected Knowledge supplies UUIDs only; authoritative Profile/Brand/Knowledge text is server-resolved.
- **INT-OAI-007** CI uses deterministic fake generation and needs no live OpenAI key.

## 4. Private Media Library integration boundary — IMPLEMENTED

Media Library is the common binary boundary for Brand Kit, Knowledge documents and generated media.

### Storage rules
- private buckets include `media-library` for operator uploads and `generated-media` for generated outputs;
- browser upload/read uses short-lived signed transport generated by authorized server/Edge boundaries;
- durable business identity is `media_assets.id` plus organization-scoped database lineage;
- raw signed URLs and browser-supplied storage paths are not persisted as Brand Kit identity or Knowledge FILE identity.

### Brand Kit consumption
- Brand Kit receives Media asset UUIDs only;
- assignment must resolve to same-org ACTIVE IMAGE media with compatible MIME;
- official logo/approved imagery remains private Media Library data until a signed preview/use URL is needed.

### Knowledge FILE consumption
- Knowledge ingestion receives same-org ACTIVE DOCUMENT Media asset UUID plus declared supported format;
- server resolves private source bytes through trusted storage access;
- PDF/DOCX/PPTX/TXT extraction occurs server-side;
- Media asset UUID remains durable source lineage while signed read URL/path remains transport-only.

## 5. URL Knowledge ingestion boundary — IMPLEMENTED

URL ingestion is an outbound HTTP integration and therefore follows a strict SSRF boundary.

### Supported source
- HTTP/HTTPS only.

### Rejected destinations
- loopback;
- private address space;
- link-local destinations;
- cloud metadata/special infrastructure targets;
- redirects resolving to unsafe destinations;
- unsupported protocols or malformed URLs.

### Extraction rules
- fetch is bounded by source/text limits;
- HTML/text is sanitized before Knowledge persistence;
- canonical safe source URL and fingerprint/metadata may be stored as source lineage;
- fetched page credentials/cookies are not supplied by PAK;
- extraction success creates DRAFT Knowledge only;
- URL content is never treated as automatically approved institutional truth.

### Explicit non-support
- generic crawler/site mirroring;
- OCR;
- XLSX/CSV ingestion;
- arbitrary authenticated/private intranet URL ingestion.

## 6. Knowledge extraction contract — IMPLEMENTED

Supported formats:
`PDF | DOCX | PPTX | TXT | URL`.

Rules:
- extraction produces bounded sanitized text;
- malformed/unsupported source maps to safe user-facing errors;
- source/extraction metadata preserves provenance but excludes private signed URLs and secrets;
- document finalization and resulting DRAFT Knowledge creation are transactional;
- activation remains separate human review.

## 7. LTX video generation — IMPLEMENTED

### Purpose
Production video-generation adapter behind provider-neutral video contract.

### Secret
- `API_KEY`

### Current execution rules
- provider/model specifics stay in adapter/worker;
- durable `video_generation_attempts` lineage;
- browser submits identifiers only;
- trusted prompt/model/duration/aspect ratio reconstructed from approved Scene Planning state;
- paid generation requires OWNER/ADMIN/EDITOR plus APPROVED, source-current, blocker-free plan/shot lineage;
- browser cannot directly insert provider attempts/jobs;
- bounded retry with protected `SUBMISSION_UNKNOWN` state;
- provider result URL is ephemeral and output must be imported into private PAK media before completion;
- unattended reconciliation uses privileged dispatcher authentication from Vault/runtime infrastructure;
- credential test is non-generation/read-only where supported.

Runtime components:
- `video-generation`
- `video-generation-retry`
- `video-generation-dispatcher`
- `pg_cron` + `pg_net`
- private `generated-media` Storage.

A real paid render remains a controlled operational acceptance check when valid org credential/credits exist; CI does not fabricate it.

## 8. Scene Planning institutional Brand integration — IMPLEMENTED

Brand Kit is an internal authoritative integration into the Scene Planning prompt/context boundary.

Rules:
- server resolves current Brand Kit for the same organization;
- palette/typography/logo treatment/brand voice/visual constraints provide institutional defaults;
- explicit Visual Bible values remain project creative-direction authority where allowed;
- official primary logo Media asset ID is carried separately and cannot be silently replaced by Visual Bible styling;
- Scene Plan snapshots persist Brand Kit revision/institutional brand context, not signed asset URLs.

## 9. Meta platform — ROADMAP-GOVERNED

Future Meta integration retains the existing requirements:
- write-only secrets in browser UX;
- server-side connection validation/token refresh;
- signature-validated webhooks;
- provider publication IDs/status persisted without access tokens;
- non-secret publication target IDs linked to Vault-backed connection(s).

## 10. Webhooks

- **INT-WH-001** Every webhook validates provider signature/authentication before business parsing.
- **INT-WH-002** Raw retention, if needed, is bounded/scrubbed.
- **INT-WH-003** Handling is idempotent by provider event ID/deterministic dedupe key.
- **INT-WH-004** Slow work is queued after durable acceptance.
- **INT-WH-005** Organization resolution comes from trusted stored provider target IDs, never untrusted organization claims alone.

## 11. Rate limiting and retries

Adapters normalize failures to stable categories such as:
`AUTH_INVALID`, `PERMISSION_DENIED`, `RATE_LIMITED`, `TRANSIENT_PROVIDER`, `INVALID_REQUEST`, `NOT_FOUND`, `CONFLICT`, `CONTENT_FILTERED`, `SUBMISSION_UNKNOWN`, `UNKNOWN_PROVIDER_ERROR`.

Retry only categories proven safe by provider/job semantics. Ambiguous external submits require reconciliation/manual handling rather than speculative resubmission.

URL ingestion differs from provider side-effect integrations: unsafe destination or validation failure is terminal and never bypassed by retry.

## 12. Credential and provenance audit

Provider credential audit records provider, organization, actor, event type, timestamp and safe metadata only; plaintext secrets never enter audit rows.

Generation provenance independently records authoritative Organization Profile/Brand/Knowledge revisions. Provider/model metadata and institutional source provenance are separate concerns and neither substitutes for the other.

## 13. Internal infrastructure credentials

Platform/runtime secrets include:
- Supabase service-role key where legacy/internal runtime requires it;
- deployment/platform credentials;
- internal generation/assembly dispatcher/worker credentials;
- environment project URL for scheduled internal dispatch.

They are not rendered as organization integrations or persisted in Brand/Knowledge records.

## 14. Integration acceptance checklist

Before enabling a new external provider/source capability:
1. typed provider/source-neutral boundary exists;
2. deterministic fake/test fixture exists;
3. role and tenant authorization are defined;
4. secret/non-secret storage boundary is explicit;
5. paid-spend/idempotency boundary is explicit where applicable;
6. connection/source validation is safe;
7. URL capabilities have SSRF policy if network destinations are user-controlled;
8. rate-limit/error/retry mapping is defined;
9. logs are secret-redacted;
10. durable identity vs ephemeral transport is defined;
11. runtime/RLS/security probes pass;
12. live smoke is controlled and residue is cleaned up;
13. any live-discovered defect is fixed with forward migration/regression test rather than rewriting migration history.
